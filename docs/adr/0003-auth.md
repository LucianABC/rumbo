# ADR 0003 — Authentication

- **Status:** Deferred — the mechanism must be decided before the first production deploy (interim decision revised 2026-11-05, revision 2)
- **Date:** 2026-10-07

## Context

The MVP has one real user (the author). GitHub is **optional**: it is used only to link roadmap projects to repos (F5, via a GitHub App installation), never as a required login. The owner set a hard limit: **rumbo does not go to production without auth**; until then it runs only on the owner's machine.

That splits the problem in two:

1. **Ownership** — every row has a `userId`, every query is scoped by it, and tests prove one user cannot reach another's data. Expensive to retrofit (every endpoint, test and screen), cheap from the first endpoint.
2. **Authentication mechanism** — how a user proves who they are (register, login, sessions, demo user). Only needed once the app is reachable by anyone other than the owner's local machine.

## Decision (interim)

- **Build ownership from the first domain endpoint.** `User` table, `userId` foreign keys, repository helpers that require a `userId`, cross-user access tests.
- **Identity port:** the API resolves the current user through an `IdentityProvider` interface (`resolveUser(request) → User | null`) used by a global guard. Handlers only ever see `userId` from the request context.
- **Local single-owner adapter:** on the owner's machine, in `pnpm dev` and in the prod-like Compose stack, the adapter returns the seeded owner user. It is enabled only when `AUTH_MODE=local-owner` **and** `DEPLOY_ENV=local`; with any other `DEPLOY_ENV`, or none, the API refuses to boot with that adapter. `NODE_ENV` plays no part: `production` describes the build, and the Compose stack runs it too, so a check on it would lock the adapter out of the environment where work is verified (#51).
- **`DELETE /api/v1/me`** is built with ownership (privacy rule), independent of the mechanism.
- **No production deploy** until a real adapter is implemented and this ADR is accepted.

## Options for the real mechanism (to decide before production)

All four are $0 at this scale. Option "Sign in with GitHub" was discarded: GitHub must stay optional.

|                                                              | A. Own (email + password, JWT cookies) | C1a. Amazon Cognito                   | C1b. Clerk     | C2. Better Auth (library) |
| ------------------------------------------------------------ | -------------------------------------- | ------------------------------------- | -------------- | ------------------------- |
| Effort                                                       | ~1.5 weeks                             | ~4–5 days                             | ~2–3 days      | ~3–4 days                 |
| User data lives in                                           | Our DB                                 | Owner's AWS account                   | Clerk (US)     | Our DB                    |
| Own security risk                                            | High                                   | Low                                   | Low            | Low–medium                |
| Lock-in                                                      | None                                   | High (password hashes not exportable) | High           | None                      |
| Coupled to the AWS exit plan (ADR 0002)                      | No                                     | **Yes**                               | No             | No                        |
| Learning value                                               | Security fundamentals                  | SAA (user pools, JWT)                 | Low            | Low                       |
| Built-ins (MFA, verification, reset, brute-force protection) | Build them                             | Yes                                   | Yes            | Plugins                   |
| Demo user                                                    | Trivial                                | Server-side login with known password | Sign-in tokens | Trivial                   |

Current recommendation: **C2 (Better Auth)** — same architecture as A (users and sessions in our Postgres, httpOnly cookies, nothing to migrate) without writing the security-critical code. Cognito if SAA practice on auth is wanted and the AWS coupling is acceptable.

## Trade-offs

- About a day of interim work (local adapter) is thrown away when the real adapter lands; everything else (ownership, guard, `DELETE /me`) stays.
- The deploy pipeline is validated later than the brief intended (see `docs/product/walking-skeleton.md`), because production waits for auth.
- Risk: the local adapter leaking into production. Production runs the same images as the Compose stack, so only runtime configuration tells them apart. Mitigated by failing closed: only Compose and `pnpm dev` set `DEPLOY_ENV=local`, and an unset value counts as deployed. A test boots the API with `AUTH_MODE=local-owner` and `DEPLOY_ENV` unset or `production` and expects failure, and the CDK stack (#16) asserts that the API task gets neither `AUTH_MODE=local-owner` nor `DEPLOY_ENV=local`.
