# ADR 0003 — Authentication

- **Status:** Proposed
- **Date:** 2026-10-07

## Context

Auth is built in phase 2, before any domain endpoint. Requirements: multi-user with ownership on everything, a **demo user an evaluator can enter without registering**, and in F5 a **GitHub App** (push webhooks, read-only contents) that the user must install on their repos anyway. Web runs on Vercel and the API on AWS behind CloudFront (ADR 0002). Until a custom domain exists, the web proxies `/api/*` to the API, so the browser sees a single origin; afterwards they move to sibling subdomains (`app.<domain>`, `api.<domain>`). Data is personal (CVs), so session theft matters more than usual for a side project.

## Options

| | A. Email + password, JWT in httpOnly cookie | B. Sign in with GitHub | C. Managed auth (Clerk, Cognito, Auth.js) |
| --- | --- | --- | --- |
| Phase-2 dependency | None | Needs the GitHub App / OAuth app set up before any feature | Vendor setup |
| Demo user | Trivial (seeded account, "Enter as demo") | Needs a separate non-GitHub path anyway | Depends on vendor |
| Target users | Anyone | Only people with GitHub (most of them, not all: AI Solutions roles are not always coders) | Anyone |
| What it demonstrates | Password hashing, cookie/session security, CSRF, rate limiting | OAuth flow | Integration |
| Work | Highest (we own resets, hashing, rotation) | Medium | Lowest |
| Reuse for F5 | None — F5 connects GitHub as a linked account | GitHub App user tokens give identity + repo access in one flow | None |

## Decision

**Option A for identity, with GitHub as a linked account in F5.** Data model allows adding "Sign in with GitHub" later without migration (`User` 1—N `AuthIdentity { provider, providerUserId }`).

Details:

- Passwords hashed with **argon2id**. Email verification and password reset are **out of the MVP** (single real user); registration is rate limited.
- **Short-lived access JWT (15 min) + rotating refresh token (7 days)**, both in `httpOnly; Secure; SameSite=Lax` cookies (host-only on the web origin while proxied; scoped to the parent domain once the custom domain exists). Refresh tokens are stored hashed in the DB, so logout and "log out everywhere" are real revocations. Reuse of a rotated refresh token revokes the whole family.
- **CSRF:** SameSite=Lax plus an `Origin` check on every non-GET request against the allowed web origin.
- **Demo user:** `POST /api/v1/auth/demo` issues a session for a seeded demo account. The demo account is reset nightly, cannot trigger LLM runs above a small budget, and cannot connect GitHub.
- The guard puts `{ userId }` in the request context; repositories require it. `GET /api/v1/me` is the first protected endpoint.
- Login/register/demo endpoints are rate limited from the first deploy.

## Trade-offs

- We own a security-sensitive surface (hashing, rotation, revocation). Mitigated with a small, well-tested module and e2e tests for the edge cases (expired access, rotated refresh reuse, cross-user access).
- No email verification means a typo'd email cannot recover the account. Acceptable for the MVP; listed in "Later".
- Users connect GitHub separately in F5 even though they may have wanted to log in with it. Minor UX cost; avoids making phase 2 depend on F5 infrastructure.
- Without a custom domain, every API call from the browser makes an extra hop through Vercel's proxy. Acceptable for the MVP; buying the domain removes it and is a config change.
